# Controlled generative UI

Eva can present plans, choices, tables, reminders, and approval requests as native interactive cards. The model never writes React, HTML, or executable UI code. It may only call a small set of tools whose inputs are validated against the shared Zod protocol.

## Data flow

1. The cloud model or Pi agent calls `present_plan`, `present_choice`, or `present_table`. Existing `schedule_reminder` and pending Bash operations produce reminder and approval cards from their verified backend result.
2. The local agent server or per-user `EvaAgent` Durable Object validates the payload and adds a typed `uiBlocks` entry to the assistant message.
3. Local JSON chat storage or D1 persists that message. `message.updated` broadcasts the canonical message to every connected client.
4. React selects an allowlisted renderer by `kind`. Unknown or invalid blocks are discarded when D1 rows are read.
5. A choice submission sends `ui.choice.submit` with the chat, message, block, and option IDs. The backend validates those IDs, marks the block submitted, persists it, and starts the follow-up turn. Reminder and approval buttons use their existing validated commands.

Hybrid device turns carry `uiBlocks` in `device.turn.complete`, so a card generated by Pi is persisted in the same cloud chat. Offline turns include the blocks in their existing message snapshot and sync them on reconnect.

## Block catalog

- `plan`: title and up to 20 steps with pending, running, complete, or error state.
- `choice`: question, 2-10 options, optional multi-select, and persisted submitted selection.
- `table`: up to 12 columns and 100 scalar rows.
- `reminder`: created only from the saved reminder returned by the reminder service.
- `approval`: created only for a persisted pending tool call; the existing tool approval policy remains authoritative.

The limits are enforced in `packages/protocol/src/index.ts`. Adding a new component requires a protocol schema, server-side creation/action validation, a renderer, persistence tests, and both compact browser and packaged desktop acceptance.

## Migration and rollback

D1 migration `0005_generative_ui.sql` adds `messages.ui_blocks_json` with an empty-array default, so old rows remain valid. Local chats require no migration because Zod supplies an empty array when old JSON files are loaded.

To roll back application code, deploy the previous Worker and desktop build. The additive D1 column may remain; older code ignores it. Do not drop it during an incident because it contains user-visible chat state.

## Future interoperability

The native protocol is deliberately transport-neutral. An AG-UI adapter can later translate `message.append`, `assistant.delta`, `tool.*`, and `message.updated` events without making CopilotKit or another UI framework the source of truth. Keep Eva's schemas and server-side action validation authoritative.
